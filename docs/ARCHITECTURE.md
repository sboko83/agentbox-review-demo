# agentbox — архитектура

Веб-платформа для запуска агентов: чат с выполнением кода, настраиваемые
политики входа и выхода, судья, массовые прогоны одного запроса на множестве
конфигураций. Параметры настроек взяты из заданий недели 1 курса.

Установка, запуск и что умеет интерфейс — [README](../README.md).

## Решения

### Агент — объект в общем процессе, не микросервис

Агент почти всё время ждёт HTTP-ответ от провайдера. Это I/O-bound задача, и
процессная изоляция на неё не нужна: сто контейнеров стартуют минуты и стоят
стократного оверхеда ради работы, которая укладывается в сто корутин `asyncio`.

Поэтому агент — обычный объект без собственного I/O наружу. Всё внешнее он
получает через порты, которые инжектятся при создании. Спавн ста агентов с
разными конфигами — создание ста объектов, миллисекунды.

Изоляция между агентами логическая: свой `AgentSpec`, своя память, свой ledger,
никаких общих изменяемых объектов. Процессная изоляция нужна ровно там, где
агент выполняет команды, и относится она к executor'у, а не к агенту.

Потолок параллелизма задаёт не процесс, а внешние ограничители: rate limit
провайдеров (общий семафор внешних вызовов), бюджет прогона (общий ledger
с лимитом) и пул executor'ов для агентов с инструментами.

### Порты

| Порт | Отвечает за | Реализации |
|---|---|---|
| `LLMPort` | вызов модели, стриминг, usage и стоимость | клиенты из реестра провайдеров; сейчас opencode Zen |
| `ToolExecutor` | выполнение инструментов в рабочей папке | локальный подпроцесс или Docker |
| `Store` | сессии, сообщения, конфиги, прогоны | SQLite |
| `EventBus` | события агента наружу, в SSE | in-process |

Ядро не знает ни про HTTP, ни про SQL, ни про браузер — как в `week-2-task-1`,
где то же разделение уже проверено на трёх файлах.

### Пайплайн

```
InputPolicy → LLM → tool-loop → OutputPolicy → Judge
```

Политики — плагины с общим интерфейсом, а не ветвления внутри агента. Иначе
сотня конфигураций превращается в сотню веток кода.

`tool-loop` находится в ядре с самого начала, а не приклеивается позже:
`OutputPolicy` обязана видеть запрошенные вызовы инструментов, а не только
текст. Запрет опасных команд, ограничение путей и урезание вывода команды перед
отправкой обратно в модель — это её работа, и добавить её задним числом значит
переписать пайплайн.

`InputPolicy` строит план запроса: прямой вызов, пошаговую инструкцию,
предварительное самосоставление промпта или три независимых роли с финальным
ведущим. Подготовительные вызовы не получают инструменты и не попадают в
историю; инструменты доступны только финальному ответу. `OutputPolicy` получает
контекст до вызова и после него, включая полный список запрошенных инструментов.
Поэтому она задаёт `text.format` и `max_output_tokens` в API-режиме либо
добавляет правила к промпту, не лишаясь возможности проверять tool-loop.

Контекст помечает вызов как финальный. Политика видит все вызовы, но формой
ответа управляет только на финальном: подготовительный вызов производит
промежуточный артефакт, а не ответ пользователю, и самосоставленный промпт,
втиснутый в JSON-схему ответа, промптом быть перестаёт. Иначе две независимые
настройки недели 1 — стратегия и контроль ответа — ломали бы друг друга.

### Две физики нагрузки

Один и тот же `AgentSpec`, разные capability и разная физика параллелизма.

| Профиль | Инструменты | Параллелизм |
|---|---|---|
| experiment run | нет | сотни; упирается в rate limit и бюджет |
| coding session | есть | упирается в пул executor'ов |

### Выполнение кода

Инструменты: `read_file`, `write_file`, `edit_file`, `list_dir`, `grep`,
`run_command`. Шесть штук закрывают сценарий Codex; расширять по факту нужды.

Рабочая папка и вид executor'а входят в секцию `tools` неизменяемой спеки. Путь
одновременно служит границей: пути всех инструментов резолвятся и проверяются
на принадлежность корню, выход наружу отклоняется до вызова executor'а.

Режимы подтверждения: `read-only` — только чтение; `ask` — подтверждение на
запись и команды; `auto` — без вопросов в пределах рабочей папки. Дефолт `ask`:
агент с доступом к shell без подтверждений опасен по умолчанию.

`run_command` запускает подпроцесс без shell: команда разбирается `shlex`, а
первое слово сверяется со списком разрешённых. Конвейеры, перенаправления и
подстановки поэтому не работают — но список разрешённых команд имеет смысл
только тогда, когда команду не может подменить `;` внутри строки.

`LocalExecutor` стартует как подпроцесс с валидацией путей, таймаутом и списком
разрешённых команд. Это не настоящая изоляция — процесс технически видит всю
файловую систему, защита держится на проверках в инструментах.

`DockerExecutor` — вторая реализация того же порта, выбранная при создании
сессии и сохранённая вместе с ней. Каждый вызов инструмента получает временный
контейнер с единственным RW-mount рабочей папки, без сети, capabilities и
записи вне mount. `--cpus`, `--memory` и `--pids-limit` ограничивают ресурсы;
числовой UID/GID хоста не оставляет root-файлов в Linux bind mount. Ядро агента
не знает, какой executor выбран. Образ собирается явно из `backend/docker`, а
его имя и лимиты задаются окружением.

### Подтверждение — второй запрос в уже открытый поток

Диалог подтверждения приходит кадром SSE, после чего генератор ответа
останавливается на `asyncio.Future`, а браузер отвечает отдельным POST, который
эту future разрешает. Альтернатива — завершить поток статусом «ждём ответа» и
продолжать новым запросом — требует хранить незаконченный шаг в базе и
восстанавливать его, то есть переизобретать продолжение корутины поверх HTTP.

Молчание — отказ: таймаут и закрытая вкладка означают «нет». Единственный
ответ, который нельзя получить по умолчанию, — «да».

### Агент собирается на каждый запрос

Агент не живёт между запросами: он создаётся заново, загружает историю из базы
и восстанавливает накопленный расход. Так состояние переживает перезапуск и
`--reload`, а расход остаётся сквозным — иначе лимит бюджета обнулялся бы при
каждой перезагрузке. Долгоживущий реестр нужен только фоновому матричному
прогону, где агент работает без открытого запроса от браузера.

### Стриминг поверх POST

`EventSource` в браузере умеет только GET, а отправка сообщения — это POST с
телом. Поэтому кадры SSE читаются из тела ответа `fetch` и разбираются вручную:
формат остаётся стандартным SSE, но запрос — обычным POST.

Разбор SSE не имеет права останавливаться на `data: [DONE]`: на
`/chat/completions` цена вызова приходит отдельным кадром уже после него, а на
`/responses` — отдельным событием `ping`. Парсер, написанный по учебнику
формата, теряет стоимость каждого запроса.

### Конфиг иммутабелен

`AgentSpec` v2 состоит из секций `model`, `sampling`, `output`, `reasoning`,
`context`, `tools`, `judge`, версионируется и хранится по хешу содержимого.
Имя принадлежит пресету, а не спеке. Старый плоский JSON переводится в v2 при
чтении; миграция SQLite переставляет ссылки сессий, пресетов и прогонов на
новые хеши, включая перенос рабочей папки и executor'а из строки сессии.

Прогон ссылается на версию конфига, а не на его текущее состояние: иначе
сравнение ста конфигураций перестаёт быть воспроизводимым. Обычная сессия может
атомарно переставить указатель на новую спеку через PATCH; сессия матричного
прогона остаётся неизменяемой. Каждая строка ledger сохраняет свой `spec_hash`
и `message_id`, поэтому последующая настройка сессии не меняет происхождение
старых ответов.

JSON для `text.format` хранится канонической строкой, а не изменяемым словарём:
иначе замороженная модель Pydantic была бы внешне иммутабельной, но её вложенную
схему можно было бы изменить после вычисления хеша. Фронт получает JSON Schema
`AgentSpec` по API и строит форму по ней; у него нет копии перечня полей.

### Провайдер — композиция трёх адаптеров

`llm/provider.py` хранит единственный реестр по имени. Его `Provider` объединяет
настроенный клиент `LLMPort`, каталог моделей и capability-map. Строка
`AgentSpec.model.provider` выбирает эту композицию при каждом вызове обычной
сессии; матричный прогон разрешает её отдельно для каждой неизменяемой спеки.
Поэтому одинаковые model id разных провайдеров не смешиваются ни в каталоге,
ни при расчёте цены: идентичность модели — пара `provider + model`.

Ключ и базовый URL принадлежат builder'у провайдера и читаются из окружения или
`secrets/.env`; общая конфигурация сервера о них не знает. Новый провайдер
требует только своих клиента, каталога и capabilities внутри `llm/` плюс одну
строку в композиционном реестре. UI получает имена провайдеров из объединённого
каталога и не содержит их закрытого списка.

### Два транспорта Zen

Zen маршрутизирует по вендору: `gpt-*` обслуживает `/responses`, остальные 45
идентификаторов — `/chat/completions`. Это не два способа сделать одно и то же:
эндпоинты по-разному называют те же параметры, по-разному раскладывают историю
диалога и по-разному сообщают цену. Выбор находится в `ZenCapabilities` и
инжектится агенту вместе с Zen-клиентом; ядро больше не определяет транспорт по
идентификатору модели.

Формат истории — единственное свойство транспорта, нужное ядру, и он заперт в двух
рендерах `Conversation`: `responses_items()` отдаёт плоский список с
`function_call` / `function_call_output`, `chat_messages()` — сообщения с
`assistant.tool_calls` и `role: tool`. Диалог хранится один; выбор рендера
делается по идентификатору модели.

### Карта возможностей вместо четырёхсотой

`ZenCapabilities` в `llm/zen.py` — таблица «транспорт → принимаемые параметры», снятая
вызовами живого API, а не прочитанная в документации. Она понадобилась, потому
что реальность оказалась резче ожидаемого: **ни одна `gpt-*` модель Zen не
принимает `temperature` и `top_p`** — все они reasoning-модели и отвечают
HTTP 400 `Unsupported parameter`. `top_k`, `seed`, `stop` и штрафы отвергаются
там же; бюджет рассуждений принимается только вложенным, как `reasoning.effort`.
На `/chat/completions` проходит весь набор, а бюджет рассуждений — плоским
`reasoning_effort`.

Непринимаемый параметр не уходит в запрос, а форма гасит его поле с объяснением:
пользователь выбрал модель, а не страницу ошибки. Обратная схема — отправить и
показать четырёхсотую — научила бы его только тому, что настройки лгут.

### Каталог моделей

Каталог показывает всё, что этот ключ действительно может вызвать: 38 из 70
идентификаторов Zen. Исключены семейства, проверенные вызовом и не работающие:
`claude-*`, `gemini-*`, `grok-*`, `muse-*` отвечают ошибкой провайдера 500/503,
а `*-free` и `big-pickle` — `MissingSessionID`. Предлагать конфигурацию, которая
гарантированно не запускается, хуже, чем не показать её вовсе; остальные id
показываются как есть, потому что перебирать семьдесят моделей пробным запросом
перед каждым открытием формы дороже, чем разобрать одну ошибку.

Zen-каталог берёт идентификаторы у Zen, а имя, цены за миллион входных/выходных
токенов и размер контекстного окна присоединяет из `models.dev` у провайдера
`opencode`; недоступность прайс-листа не скрывает модель. Реестр добавляет к
каждой записи имя провайдера и объединяет настроенные каталоги. Окно нужно
панели токенов: без потолка полосу заполнения нечем закончить.

Потолок цены живёт в реестре, а не в адаптере вендора: это решение установки о
том, сколько она готова платить, и оно должно одинаково действовать на любого
следующего провайдера. `AGENTBOX_MAX_MODEL_PRICE` (по умолчанию 5 $ за 1M
входных токенов, `0` снимает ограничение) не удаляет модель, а гасит у неё флаг
`offered`. Удаление строки унесло бы вместе с моделью её цену и окно, а их
читают оценка матричного прогона и счётчик контекста уже открытой сессии.
Ограничение идёт по входному токену: в длинном агентском диалоге вход
доминирует в счёте, поэтому одной оси достаточно. Неизвестная цена модель не
гасит — перебой `models.dev` не должен опустошать форму.

Форма показывает `offered`-модели плюс ту, что уже выбрана. Без этого открытие
старой сессии с подорожавшей моделью показало бы первый пункт списка, а
debounce-PATCH молча переставил бы спеку на другую модель.

### Деньги

Прогон на сотне конфигураций стоит реальных денег, и остановить его после
старта дешевле, чем объяснить счёт. Перед запуском считается оценка
(конфигураций × повторов × цена модели по `models.dev`), она показывается и
требует подтверждения; во время прогона общий ledger режет выполнение при
достижении лимита.

### Judge и подтверждаемая матрица

Judge — отдельный вызов `LLMPort` после финального ответа агента, а не новая
ветка chat-пайплайна. Он получает исходную задачу, настраиваемые критерии и
ответ, возвращает JSON с баллом 0–10 и объяснением; порог хранится в том же
неизменяемом `AgentSpec`. Если ответ ниже порога, политика явно выбирает ровно
одно из трёх действий: отдать исходный ответ, сделать один повтор или вызвать
запасную модель и снова оценить. Некорректный ответ судьи не маскируется как
провал качества: он остаётся в отчёте как недоступный вердикт, без
автоматической дополнительной траты.

`POST /api/runs/estimate` строит верхнюю оценку: учитывает число внутренних
вызовов стратегии, Judge и один сценарий восстановления. Цены берутся из текущего
отобранного каталога; если для модели нет обеих цен, запуск не предлагается.
Ответ содержит одноразовый идентификатор оценки. `POST /api/runs` принимает только его,
поэтому конфигурацию нельзя подменить между ценой на экране и платным вызовом.
Фактические `cost` и usage от выбранного провайдера пишутся в `ledger` с `run_id`; отчёт сравнивает
только эти измерения, не расчёт до старта.

### Пул агентов

Подтверждённый матричный прогон запускается в фоне через `RunSupervisor`. На
каждую пару «конфигурация × повтор» он регистрирует
отдельного агента со статусом `queued`, `running`, `completed`, `failed` или
`budget_stopped`. Реестр живёт в процессе и нужен только для наблюдения за
активным прогоном; итог, конфигурации и фактический ledger по-прежнему сразу
пишутся в SQLite.

Ячейка попадает в SQLite при любом исходе, включая упавший. Потерянная ячейка
молча уменьшила бы знаменатель каждой доли в отчёте, поэтому провал и остановка
по бюджету хранятся как прозрачные пустые ячейки с текстом причины, а не
исчезают из матрицы.

`ProviderGate` — один семафор на весь процесс, а не на run или Agent. Он
оборачивает каждый `LLMPort.stream`, поэтому параллельность ограничивает именно
внешние вызовы всех провайдеров, включая обычный чат. `SharedBudget` принадлежит одному run и учитывает
фактический `cost` только после завершения вызова. Перед входом в семафор и
после ожидания он проверяет лимит; достигнутый общий бюджет не запускает
следующий provider call, а ожидавшие агенты получают `budget_stopped`.

`ExecutorPool` тем же способом оборачивает `ToolExecutor` кодовых сессий.
Очередь ограничивает одновременные подпроцессы, не меняя API executor'а и не
привязывая ядро к локальной реализации. Лимиты процесса задаются
`AGENTBOX_PROVIDER_CONCURRENCY` (по умолчанию 4) и
`AGENTBOX_EXECUTOR_CONCURRENCY` (по умолчанию 2). Дашборд опрашивает состояние
агентов, общий расход и размеры обеих очередей отдельным API, а сравнительный
отчёт остаётся его финальным экраном.

### Экспорт отчёта

Отчёт прогона выгружается из сохранённой SQLite-модели, а не из текущего
состояния дашборда. JSON содержит полный неизменяемый запрос, конфигурации,
результаты и агрегаты; CSV содержит одну строку на пару «конфигурация ×
повтор», включая вердикт и фактическую стоимость. Поэтому экспорт доступен и
после перезапуска процесса, когда in-memory dashboard уже пуст.

### Конфигурация, библиотека и диагностика

Настройка агента и управление общими объектами требуют широкой формы;
контекст и память нужны рядом с конкретным ответом. Поэтому конфигурация и
библиотека занимают отдельные экраны, а диагностика открывается рядом с чатом
по запросу. Лента остаётся ограниченной по ширине. Формы сохраняют черновики
при навигации, применение явно отделено от редактирования.

До первого сообщения конфигурация остаётся в черновике браузера:
сессия и её неизменяемая `AgentSpec` создаются вместе с первой отправкой.
Применение к открытой обычной сессии создаёт или переиспользует
неизменяемую `AgentSpec` и атомарно переставляет `sessions.spec_hash`. История
не переписывается, а каждая строка ledger хранит хеш реально использованной
версии. Сессии матричного прогона остаются только
для чтения, потому что их конфигурация входит в подтверждённый снимок запуска.

### Повтор эксперимента фиксирует условия

Сохранённый эксперимент хранит значения спеки и профиля, а не изменяемые
указатели библиотеки. Повтор получает копию профиля и отдельную область
долговременной памяти, чтобы один прогон не обучал следующий. При старте из
контрольной точки диалог, рабочая память и задача берутся на её сообщении;
долговременная память — из сохранённого снимка эксперимента. Она не имеет
истории по сообщениям сессии, поэтому эти два момента различаются явно.
`POST /api/sessions/{id}/fork` принимает необязательный `spec` и устанавливает
его при копировании: последующий PATCH мог бы заново извлечь рабочую память
из истории и тем самым изменить исходные условия. Без `spec` обычная ветка
сохраняет прежнее поведение. Конфигурации экспериментов хранятся в браузере;
контрольная точка зависит от сохранности исходной сессии на сервере.

### Имя принадлежит пресету

Пресет агента — именованный указатель на хеш спеки. Обновление пресета
сначала сохраняет новую неизменяемую `AgentSpec`, затем атомарно переставляет
указатель. Сессия копирует только хеш выбранной версии, поэтому переименование,
обновление или удаление пресета не меняет уже начатые диалоги и сохранённые
прогоны. Единственный пресет по умолчанию применяется только при создании
сессии без явных `preset_id` и `spec`.

Имя не входит в `AgentSpec`: одинаковая конфигурация под разными именами должна
иметь один хеш, а удаление имени не должно удалять версию, на которую ссылается
сессия. Поэтому именуется изменяемый указатель-пресет, а не содержимое спеки.

### Профиль пользователя — рядом с памятью, не в спеке

`AgentSpec` описывает агента, профиль пользователя — человека и желаемую форму
ответа. Включение профиля в спеку размножило бы пресеты по сочетанию «агент ×
человек» и делало бы смену пользователя изменением агента. Поэтому сессия
хранит указатель на `user_profiles`, а неизменяемая версия профиля адресуется
хешем содержимого. Правка указателя действует в связанных сессиях со следующего
хода; ledger фиксирует хеш реально использованной версии.

Профиль стоит после роли и перед памятью, участвует в ответе, подготовительных
стадиях и планировании, но не в сводке и Judge. Машинный контракт `OutputPolicy`
важнее профиля; явная просьба текущего сообщения важнее стилевого предпочтения,
но неявный выбор языка вопроса — нет. Роутер может только предложить изменение
профиля, а новая версия появляется после подтверждения человеком.

### Инварианты принадлежат сессии

Инварианты описывают обязательные границы задачи, а не агента или человека,
поэтому не входят ни в `AgentSpec`, ни в профиль, ни в обучаемую память. Полный
набор адресуется хешем содержимого; сессия хранит текущий хеш, а история
назначений — каждую явную смену. Запись принимает ожидаемый хеш и отказывает
устаревшему редактору вместо молчаливого перезаписывания.

Ветка копирует хеш исходной сессии и затем меняется независимо. Матричная
котировка фиксирует полный набор вместе со спеками и профилями, а ledger хранит
его хеш для каждого вызова. Изменение при активной задаче одновременно требует
явного возврата в `planning`, потому что прежний план проверялся при других
условиях.

Полный блок правил стоит перед профилем и памятью и не участвует в их бюджетах.
Одна версия фиксируется на весь ход: основной ответ, подготовительные стадии и
трекер не могут увидеть разные наборы. Смысловой проверяющий работает до ответа
и до изменяющего инструмента; его ошибка закрывает действие, а не разрешает.
Кандидат ответа буферизуется до вердикта, поэтому отклонённый текст не утекает
через SSE. Форматированный отказ проходит обычный контракт ответа. Проверка не
доказывает соблюдение произвольного правила: её результат, ID, причина и
стоимость сохраняются отдельно, чтобы решение можно было проверить вручную.

### Матричный прогон фиксирует конфигурацию

Матричная котировка принимает упорядоченный список пресетов и сразу разрешает
его в снимок спек. Между показом цены и подтверждением пресет может измениться,
но одноразовая котировка продолжит запускать именно оценённые версии.

Матричный прогон — отдельный экран, а не блок в ленте: он не часть диалога и
делить с ним прокрутку ему незачем.

Состояние диалога вынесено в хук `useChatSession`, компоненты раскладывают
разметку и больше ничего. Следующая правка вёрстки не должна проходить сквозь
разбор SSE.

Контекст показывается в двух масштабах из одного `ContextView`: движущаяся
граница прямо в полной стенограмме отвечает, какие записи уже не уйдут модели,
а правая вкладка раскрывает собранный payload следующего вызова. Метрики ответа
берутся по связи `ledger.message_id → messages.id`, поэтому они остаются рядом
с тем ответом и той версией спеки, которыми были получены.

### Оценка контекста до вызова, факт после

Точный токенизатор всех моделей Zen локально недоступен, а решение об обрезке
принимается до запроса. Поэтому Agentbox оценивает токены по сериализованному
payload и делит вход на роль, прежнюю историю и текущий запрос. Коэффициент
«символов на токен» калибруется по фактическому `prompt_tokens` и хранится в
сессии: пересоздание Agent на следующем HTTP-запросе не сбрасывает обучение.

Полная стенограмма не обрезается в памяти агента и SQLite. Порт
`ContextStrategy.build(history, state)` строит отдельный `ContextView`: роль,
слои памяти, дословный хвост с первым `seq`, исключённые `seq` и оценку
токенов. Встроенные плагины `none`, `window`, `tokens`, `summary` отличаются
только выбором этого среза; поэтому смена стратегии в живой сессии снова видит
всю историю. Граница проходит только перед пользовательским вопросом, а вызов
инструмента с результатом хранится одной записью и не может быть разорван.

У жёсткого лимита два источника. `context.window_tokens` задаёт искусственное
окно для воспроизводимого эксперимента; без него используется окно модели из
`models.dev`. `overflow` применяется после выбранной стратегии: `drop` сужает
только текущий `ContextView`, `fail` останавливает запрос до платного вызова,
`send` передаёт неизменённый payload и сохраняет ошибку провайдера в `Failed`.
Если роль и последний пользовательский ход не помещаются, `drop` также обязан
отказать. Фактический `ContextView` приходит событием SSE `context` перед
первым `delta`; текущее представление также входит в ответ сессии.

`ledger` хранит рядом оценку, фактический usage, latency, окно и число выпавших сообщений
для каждого пользовательского ответа. Поэтому вкладка контекста восстанавливается
после перезапуска и показывает не только накопительную стоимость, но и причину
расхождения оценки с фактом. В SSE отдельное событие `usage` идёт перед `done`:
текст уже закончен, ledger уже обновлён, а интерфейс не ждёт повторной загрузки
сессии, чтобы обновить счётчики.

### Сводка вместо потери старой истории

Плагин `context.mode=summary` отделяет долговременную память от дословного хвоста.
За последними `keep_last_messages` Agentbox накапливает старые записи; когда их
становится `summary_every`, отдельный вызов `summary_model` получает предыдущую
сводку и новую порцию диалога. Основной payload после этого идёт в порядке
«роль → сводка → свежие сообщения». Между свёртками несжатый остаток также
остаётся в payload: периодичность не должна превращаться в тихую потерю фактов.
Граница не разрезает пару «вопрос — ответ», а инструменты summary-модели не
передаются.

Каждая сводка записывается новой строкой `session_summaries` с версией,
последним покрытым `messages.seq`, числом покрытых сообщений и фактическими
выходными токенами. Перезапись одной строки не позволила бы сравнить момент до
и после потери факта и расследовать ошибочную свёртку. Старые сообщения из
`messages` не удаляются: версии меняют только то, какой срез получает модель,
а стенограмма и воспроизводимость сохраняются. Стоимость summary-вызова
записывается в `ledger` с отдельным `kind=summary`, поэтому экономия входа и
добавочная цена сжатия видны независимо.

### Три слоя памяти вместо одного режима

`context.mode` управлял памятью и обрезкой сразу: включить сводку и факты вместе
было нельзя, а «факты» жили внутри сессии и умирали вместе с ней. v3 разводит
это на две оси. Стратегия владеет только **краткосрочным** слоем — дословным
хвостом и сводкой выпавшего. **Рабочий** и **долговременный** слои живут в
секции `memory` и складываются в тот же `ContextView` независимо от стратегии,
поэтому смена `window` на `summary` не включает и не выключает память.

| Слой | Что хранит | Ключ | Когда исчезает |
|---|---|---|---|
| краткосрочный | хвост диалога и сводка выпавшего | сессия | обрезка окна, overflow |
| рабочий | данные текущей задачи | сессия | явное завершение задачи |
| долговременный | сведения о человеке, решения, знания | пространство памяти | явное «забыть» |

Долговременный слой ключуется пространством, а не сессией: в этом и состоит его
отличие от рабочего — новая сессия того же пространства уже знает человека. Без
этого «долговременная память» была бы третьим именем для той же session-памяти.
Одна таблица `memory_versions` хранит оба слоя и различает владельца
условием «либо `session_id`, либо `scope_id`»: версионирование, слияние и
происхождение у них общие, а владение — разное.

Payload идёт от стабильного к изменчивому — «роль → профиль пользователя →
долговременная → рабочая → состояние задачи → сводка → последние сообщения»:
реже всего меняются профиль и долговременный блок, поэтому они остаются
кэшируемым префиксом. Каждый блок — отдельное system-сообщение с заголовком,
так что слой виден и модели, и во вкладке контекста.

У каждого слоя свой бюджет блока (`working_max_tokens`, `longterm_max_tokens`),
и режет он именно payload, а не хранилище: слой копит ключи ходами, а платится
за него каждый вызов, поэтому предел принадлежит блоку, а не доброй воле
роутера. Сверх бюджета уходит самый старый элемент — только что
маршрутизированные ключи и есть то, о чём текущий ответ. Вытесненные ключи
остаются в версии, видны в панели и называются отдельно, чтобы «слой полон» не
читалось как «памяти нет».

Счёт идёт по тому же списку блоков, которым идёт рендер: слой нельзя отправить
не посчитав и посчитать не отправив. Поэтому у каждого слоя своя оценка вместе
с заголовком, а хвост стоит ровно того, что в хвосте лежит, — раньше память
пряталась внутри его числа и рост памяти читался как рост диалога. Сумма блоков
меньше измеренной оценки запроса на разметку транспорта и схемы инструментов;
эта разница отдаётся отдельным `overhead_tokens`, а не размазывается по слоям.

Элемент памяти — `ключ → {значение, вид, origin, seq}`. `origin` (`router`,
`manual`, `promote`, `migration`) отвечает на вопрос, кто его туда положил;
переформулировка значения не меняет вид, под которым ключ уже был
маршрутизирован. Слияние осталось тем, что доказало необходимость раньше:
дешёвая модель возвращает только затронутые ключи, они накладываются на
предыдущую версию, и ключ уходит только по явному пустому значению.

Вид — словарь своего слоя: `goal`, `constraint`, `step`, `artifact`, `blocker`
у рабочего, `profile`, `decision`, `knowledge` у долговременного. Названный
роутером чужой вид не принимается молча и не превращается в нейтральный: ключ
отклоняется с именем, остальной ответ записывается, а отклонённые ключи уходят
в поток. Новый ключ без вида отклоняется так же — маршрут должен быть назван, а
не угадан здесь. Вид уже лежащего ключа наследуется, поэтому переформулировка
не требует нового маршрута. Память без видов, пришедшая из миграции, получает
вид своего слоя на входе: иначе унаследованный чужой вид отклонял бы каждую
последующую правку мигрированного ключа.

`MemoryRouter` — отдельный дешёвый вызов после завершённого хода, а не
инструмент отвечающей модели: память должна заполняться независимо от того,
включены ли инструменты, а решение о маршруте — проверяться вне собственного
ответа модели. Слой называет сам роутер отдельным ключом верхнего уровня:
ответ без имени слоя — не маршрутизация, и он отклоняется целиком, вместо того
чтобы эвристика здесь раскладывала факты по слоям за модель. Роутера спрашивают
только о включённых слоях, а `longterm_write=manual` выводит долговременный
слой из вопроса совсем — платить за решение, которое некому прочитать, незачем. Бюджеты `summary_max_tokens` и `memory.max_tokens` ограничивают
видимый результат: в `max_output_tokens` служебного вызова к ним добавляется
постоянный запас на reasoning, иначе reasoning-модель тратит весь лимит на
размышление и возвращает пустую строку. Пустой ответ — ошибка с указанием
бюджета.

Каждое обновление добавляет строку `memory_versions` с монотонной версией и
последним покрытым `messages.seq`; предыдущие версии и полная стенограмма
остаются неизменными. Ручная правка идёт тем же путём версий, но без фиктивного
расхода, и отличается только `origin`. Версия измеряется тем, что в ней лежит,
независимо от того, кто её написал; цена самого вызова роутера живёт в `ledger`
как `kind=memory` и не подменяет собой размер памяти. Новая версия публикуется
событием SSE `memory` до `done`. Ошибка разбора не отменяет уже сохранённый
ответ: поток сообщает `memory_error`, а предыдущая версия остаётся активной.

Сколько диалога роутер уже прочитал — свойство сессии
(`sessions.memory_covered_seq`), а не версии слоя: долговременная версия
принадлежит пространству и её собственный `covered_seq` считает чужой диалог.
Ветка наследует отметку не дальше своего последнего сообщения.

Запись в долговременный слой проходит через `longterm_write`. При `confirm`
роутер кладёт кандидатов в `memory_proposals` — по строке на ключ, новый
кандидат вытесняет прежний, — и слой не меняется, пока человек не примет.
Память, переживающая диалог, не заполняется сама. Принятый кандидат даёт версию
с `origin=manual` при элементе с `origin=router`: версия помнит, кто записал,
элемент — кто его сочинил. Кандидат адресуется через свою сессию, иначе чужой
идентификатор решал бы судьбу чужой памяти. Рабочий слой — данные текущей
задачи, он пишется сразу: подтверждать каждый шаг собственной задачи дороже,
чем его поправить.

Рука правит память точечно, а не пересылкой слоя: «запомнить», «забыть» и
перенос меняют один ключ, потому что копия слоя в браузере успевает устареть за
один ход роутера и воскресила бы то, что он только что убрал. Вид принадлежит
элементу, а не слою: в одном слое лежат элементы разных видов, и перезапись
слоя не должна их переклеймить. Нетронутый элемент сохраняет прежний маршрут —
ручной становится ровно та запись, которую рука изменила. Перенос между слоями
пишет по версии в каждый слой и даёт элементу `origin=promote` с `seq`
источника: факт не меняет происхождения оттого, что сменил слой, и не выдаёт
себя за свежую ручную запись. Опустевший слой остаётся версией, но блоком в
payload не идёт — заголовок над пустым объектом стоил бы токенов, не сообщая
ничего.

Сессия вступает в пространство при создании, а не при первой долговременной
записи: иначе «новая сессия в том же пространстве» зависела бы от того, успел ли
роутер что-нибудь записать, а карточка слоя не могла бы показать, скольким
сессиям эта память видна.

«Завершить задачу» — не очистка слоя: отмеченные элементы уезжают в
долговременный слой переносом, остальные уходят вместе с задачей, а слой
получает пустую версию. Версия, а не удаление: закрытая задача остаётся
читаемой в цепочке. Отметка прочитанного роутером при этом не сдвигается —
диалог он уже прочитал, поэтому детали закрытой задачи не возвращаются на
следующем ходу, а то, что должно было её пережить, лежит уже в другом слое.

Включение рабочего слоя в непустой сессии один раз извлекает память из всей
текущей истории, и только успешный результат переставляет `sessions.spec_hash`:
неудачная миграция контекста не оставляет интерфейс в режиме, которого ещё нет.

Ретировавшийся `context.mode=facts` мигрирует в «окно + рабочий слой» — та же
конфигурация, разобранная на две оси, даёт тот же payload. Миграция переносит
`session_facts` в `memory_versions` с `origin=migration`, переименовывает
`ledger.kind` и переадресует каждую спеку: секция `memory` изменила канонический
JSON, а значит и хэш, и оставленные старые дайджесты раздвоили бы каждую
конфигурацию при первой правке.

### Ветка — снимок истории, не фильтр родителя

Ветка хранится отдельной сессией с `parent_id` и `fork_seq`. При создании она
копирует сообщения и вызовы до выбранного `seq`, а также только те версии
сводки и рабочего слоя, чей `covered_seq` уже достигнут в этой точке.
Долговременный слой ветка не копирует, а делит с родителем вместе с
пространством: слой принадлежит пространству, и копия развела бы одну память на
две расходящиеся. Профиль наследуется как указатель: ветка продолжает говорить
с тем же человеком и видит следующую подтверждённую версию профиля.

Активная задача восстанавливается из последнего снимка журнала не позже
`fork_seq`, а не из текущей строки родителя: ветка от шага 2 не получает
результат шага 3. Терминальная задача не открывается заново. Ссылка на
неизменяемую `AgentSpec` сохраняется, но `run_id`, ledger и checkpoints не
переносятся: они принадлежат исходной линии, а не общей стенограмме.

Ledger не копируется. Расход описывает вызовы конкретного продолжения, поэтому
новая ветка начинает с нуля, а стоимость родителя остаётся на его строке в
дереве. Физическая копия вместо фильтра по родителю позволяет после развилки
независимо менять AgentSpec, память и историю без условий во всех запросах к
контексту.

### Задача — автомат с журналом

Этап принадлежит отдельной задаче с состояниями `planning → execution →
validation → done`; `cancelled` — отдельный терминальный исход, а пауза — флаг,
который возвращает на тот же этап. Чистый автомат вычисляет допустимые переходы
и ожидаемое действие; API, UI и трекер не держат собственных таблиц правил.

Утверждение связывает хеш плана с текущей версией инвариантов. Ревизия задачи
делает переход атомарным: устаревшая кнопка, повторный или параллельный запрос
получают объяснимый отказ, который тоже остаётся в append-only журнале.
`force` не обходит незавершённые шаги и отсутствие актуального `pass`; изменение
плана снимает утверждение, изменение результата или шагов — прежний вердикт.
Пауза меняет только управление: этап, утверждение, результат и вердикт
сохраняются. Поздний трекер и инструмент сверяют ревизию перед записью.

В `planning` и на паузе инструментов нет. На `validation` доступны безопасные
операции чтения; `run_command` скрыт, потому что общий executor не гарантирует
отсутствие записи. Закрытие или отмена задачи завершает рабочий слой памяти.

План разбирается в шаги и критерии детерминированно; неразобранный текст остаётся
черновиком и не открывает выполнение. Отдельный дешёвый трекер отмечает шаги и
вердикт после хода, но каждое его решение снова проверяет автомат. Ошибка
трекера публикуется отдельно и не отменяет уже сохранённый ответ агента.

### Стек

Бэкенд — FastAPI на `asyncio`: это и есть механизм параллельных агентов, без
потоков и процессов. `AgentSpec` описан моделью Pydantic, её JSON Schema
отдаётся фронту, и форма настроек генерируется из схемы — иначе полтора десятка
параметров пришлось бы синхронизировать между бэкендом и UI вручную.

Фронт — React + TypeScript на Vite, стриминг через SSE.

Транспорт к opencode Zen переносится из `week-2-task-1`: вендорная маршрутизация
`/responses` против `/chat/completions`, стоимость отдельным событием SSE,
подмена `User-Agent` из-за Cloudflare — всё это уже отловлено, и повторять
отлов на другом языке смысла нет. Сам HTTP переписан с `urllib` на `httpx`:
блокирующий вызов занимал бы поток на всё время ответа модели и обнулял смысл
общего процесса.

Аутентификации нет: платформа работает на `localhost`.

### Хранилище

SQLite: `agent_specs`, `agent_presets`, `user_profile_versions`, `user_profiles`,
`invariant_versions`, `session_invariant_assignments`, `invariant_checks`, `sessions`, `messages`,
`session_summaries`, `memory_scopes`, `memory_versions`, `memory_proposals`,
`tasks`, `task_transitions`, `checkpoints`, `tool_calls`, `runs`, `ledger`,
`run_configurations`, `run_results`. Сессия хранит ссылки на спеку, профиль,
инварианты и пространство памяти, а также калибровку оценки токенов; состояние
и история задачи живут отдельно. Поэтому перезагрузка вкладки или процесса не
сбрасывает текущий шаг и точность следующей оценки.
Строка `messages` с ролью `tool` — только отметка места в диалоге; сам вызов
живёт один раз, в `tool_calls`, и подтягивается по `message_id`. Так порядок
реплик и данные вызова не расходятся при перезагрузке сессии.
Без сервера, из стандартной библиотеки, файл вне репозитория. Прогоны стоят
денег и должны переживать перезапуск, поэтому персистентность нужна с самого
начала. Модель данных совместима с Postgres, если понадобится.
